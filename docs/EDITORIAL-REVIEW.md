# AI 纪年：线索、证据与入库

GitHub Actions 自动收集 **待审线索**，不替编辑判断事实，也不直接更新 `data/timeline.json`。候选报告中的 `observedDate` 是观察到的文章、简报或订阅日期，不是认定的事件日期。

## 优先从哪里找

| 来源 | 用法 | 不能证明什么 |
| --- | --- | --- |
| 厂商公告、发布日志、模型卡、官方代码库、API 停用文档 | 确认型号、可用日期、入口、阶段、许可或停用范围 | 厂商自测不能当作独立评测 |
| 论文原文、DOI、期刊版本记录与原始研究机构 | 区分预印本、正式发表、实验结果、演示；核对题目、作者和限制 | 仅有论文预印本不等于同行评审通过；体外实验不等于临床结果 |
| TLDR AI、Latent Space / AI News、36氪、Hugging Face 博客 | 拓宽发现，沿链接回原文；筛掉赞助、教程和纯转述 | 两份简报转述同一篇公告仍只是一条证据 |

可运行订阅和人工补查入口见 [来源配置](../config/discovery-sources.json)。新增订阅先用同一个解析器试跑：确认会返回有日期的条目、近期仍更新、来源稳定且没有被转载或推广淹没。优先补覆盖盲区，不按数量凑名单。

## 怎么使用候选文件

1. 先看 `REVIEW.txt` 底部的订阅状态。能解析但近期 0 条与抓取失败是两回事；失败的来源走人工补查，不能当作该机构没有发布。
2. 新候选先看厂商原始公告、正式版本或论文；Gemini CLI、vLLM 的常规补丁和预发布版本不进入新增订阅的候选，协议条目仅追踪带日期的正式版本。
3. 「已引用的官方链接」单独列出最多 12 条，并标出既有事件 ID。链接再次出现不等于官方页面已更新；用于人工检查该原文是否覆盖不同渠道或阶段。简报转载不会进入这列，也不增加证据数。
4. `candidates.json` 供脚本或编辑核对。公开发布仍须满足下述规则，不把候选直接写入纪年。

### 科学突破优先复核

- 每天 UTC 02:27 尝试抓取（GitHub 定时执行可能延迟）。报告开头有独立的「重大科学主张」队列，优先于版本发布列表审阅。它是提示，不是验证状态。
- 陶哲轩博客、Simon Willison 数学专题和 Quanta 数学频道负责补发现，Lean 社区博客提供正式核验声明。看到重大证明消息，按「作者公开主张 → 机器证书核验 → 专家复核/机构认定」分别记录，不用标题里的“已证明”替代状态。
- 若一条线索得到明确处置，发布能核实的部分，或在编辑记录注明保留原因；不要在候选清单里无声跳过。黎曼猜想案例最初已出现在 Nature、TLDR 与 Latent Space 的候选中，漏在审校而不是抓取。

## 每条候选怎么核对

1. **拆成可证实的事实。** 记录谁、什么、哪天、对谁、通过什么入口、什么阶段。区别公告日、网页更新日、定向开放日、全面开放日；同一对象在不同渠道的开放时间可分开记。
2. **逐项回原文。** 主来源必须直达相关段落、条目或论文，不只指向官网首页。登记一手链接、它支持的事实和对应日期；发布日期不明确时，不拿新闻日期补。
3. **用第二条证据对照关键细节。** 优先查独立的原始记录；例如公告对照 API 日志或模型卡、论文对照期刊版本记录。两个厂商自有页面可以互证渠道与日期，但仍属于同一组织；若是性能比较或争议性判断，找独立证据，否则只保留明确归属的陈述，或不收录。仅一份原始公告明确证实的简单事件可收，只写它确实证明的事实。
4. **冲突先不入库。** 若日期、阶段或对象不一致，先排查时区、分批开放和渠道差异；仍无解就标待审，不在无证据时选一个日期。未能核实的细节不写。
5. **查重并判定是否为里程碑。** 按机构＋对象＋阶段＋日期检索历史；同一篇原文可能支持多个不同事件。只有能力、可用性、研究结论或生态变化确有意义的条目才入库。
6. **保留审校链。** 将实际用到的一手证据写进 `sources`；事实与厂商评价分开写。修订保留旧 ID，运行 `npm run validate`，再走正常提交和 Pages 部署。

## 什么时候更新脉络

脉络是**一条有主题的小时间线**，不是厂商名单，也不是因果图。常规事件只维护 `data/timeline.json`。只有事件能说明某个主题的新阶段、补上缺失的转折，才更新 [脉络表](../data/threads.json)。可以是同一厂商，也可以跨厂商；同厂商或时间接近本身都不是收录理由。

- 每条脉络只存稳定的 `id`、主题 `title` 和按日期从早到晚排列的 `eventIds`。标题、日期、事实和来源从原事件取，不重复存；同一天按阅读顺序排。同一事件可被不同脉络引用，不可在同一条中重复。
- 每次入库、修订日期或合并事件时，检查会不会影响现有脉络。可补中间一站，不必只追加最新一站。只在证据支持的范围内写演进；不要从先后顺序或 `relatedIds` 推断因果。候选发现工作流既不接线，也不自动发布。
- 发布工作流运行 `npm run validate`，拦截不存在的事件、重复编号、同一脉络重复引用和日期倒序。编辑负责判断「这站为什么在这里」，检查程序只负责结构与顺序。首条例子是「从对话框到 API」。

### 案例：GLM-5.4

线索出现在 11 月 25 日的简报。回看 [智谱技术公告](https://z.ai/blog/glm-5.4)和 [ZCode 4.0 发布日志](https://zcode.z.ai/en/changelog)，两份原始材料都指向 11 月 23 日；前者说明通用 API 和公开权重当时未发布，后者确认 Coding Plan 渠道可用。因此纪年记 11 月 23 日的发布，不写成全面 API 开放，也不把简报日写成事件日。
